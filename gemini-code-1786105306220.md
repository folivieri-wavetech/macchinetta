# 📖 DOCUMENTAZIONE MASTER: PROGETTO "MACCHINETTA IG" (Fiordok Trading)

## 1. VISIONE GENERALE E COMPONENTI
Il progetto è un Bot di trading semi-automatizzato scritto in Python che opera sul broker **IG** tramite le loro REST API ufficiali, ed è strutturato in più componenti autonome per garantire sicurezza, testabilità e scalabilità.

### Componenti Principali (Produzione):
1. **Il Motore (`Motore.py`)**: L'anima in background che dialoga con i mercati, calcola i livelli, esegue le operazioni e gestisce il ciclo di vita (Fasi) della strategia.
2. **La Dashboard (`Dashboard.py`)**: L'interfaccia utente web creata con **Streamlit**. Permette la lettura dei dati in tempo reale, la modifica dei parametri a caldo, il Recovery manuale e la consultazione delle statistiche.

### Componenti di Testing (Sviluppo & Simulazione):
3. **Il Simulatore (`Simulatore.py` / `Simulatore.exe`)**: Un ambiente isolato che replica localmente il comportamento del broker IG. Permette di testare l'algoritmo del Motore senza effettuare vere chiamate API e senza rischiare capitale, mantenendo uno stato interno di posizioni e ordini (`CASSA_SIMULATA`).
4. **Il Backtester (`Backtester.py`)**: Simile al Simulatore ma ottimizzato per la velocità di calcolo (es. disabilita le print e carica la memoria interamente in RAM) per test su dati storici o per stress test massivi.
5. **Utility (`cerca_epic.py`)**: Uno script di supporto per ricercare gli ID degli strumenti IG (Epic) da inserire nelle configurazioni.

Le componenti in produzione **NON comunicano tra loro direttamente in RAM**, ma si scambiano informazioni scrivendo e leggendo file `JSON` e `CSV` locali. Questo garantisce che se la Dashboard crasha o viene chiusa, il Motore continua a operare indisturbato.

## 2. ARCHITETTURA MULTI-CONTO E FILE SYSTEM
Il sistema è progettato per gestire infiniti conti contemporaneamente (sia DEMO che REALI). 
Ogni conto è una cartella fisica (es. `FIORDOK_DEMO/`, `BONGIOLO_DEMO/`). All'avvio, il Motore riceve come argomento il nome della cartella (`python Motore.py FIORDOK_DEMO`). La Dashboard scansiona la root e crea un menu a tendina per saltare da un conto all'altro.

**File di scambio all'interno della cartella del conto:**
*   `.env`: Contiene i segreti (`IG_USERNAME`, `IG_PASSWORD`, `IG_API_KEY`, `NTFY_TOPIC`). Non va mai condiviso.
*   `token_ig.json`: Memorizza i token temporanei di IG (CST e X-SECURITY-TOKEN).
*   `memoria_parametri.json`: È il "ponte di comando". La Dashboard vi scrive dentro i parametri (TP, OPP, DTS) e i comandi manuali (es. KILL SWITCH, RIPRENDI). Il Motore lo legge per sapere cosa fare.
*   `stato_sistema.json`: Il Motore vi scrive dentro i prezzi live, il P/L, i margini e l'orario di aggiornamento. La Dashboard lo legge per renderizzare l'interfaccia.
*   `storico_operazioni.csv`: Database delle operazioni chiuse con P/L.
*   `console_live.log`: File di testo aggiornato dal Motore stampato in tempo reale sulla Dashboard.

## 3. LA LOGICA DI TRADING (IL VOCABOLARIO)
La strategia è un sistema di mitigazione del rischio multilivello e multi-size. Il Motore si sposta da uno stato all'altro (Fasi) autonomamente.

*   **Size (S_Core):** La grandezza base dell'operazione (es. 4 contratti).
*   **Mezza Size (S_Mezzo):** La metà della Core (es. 2 contratti). Usata per Assicurazione, Ticket e Satelliti.
*   **Quarto di Size (S_Quarto):** (es. 1 contratto). Usata per i Sat 2 (OverLoss).

### Le Fasi Principali:
1.  **FASE 1 (Ingresso):** Il sistema piazza una posizione `Core` a mercato e un'ordine pendente detto `Micro` o `Assicurazione` (S_Mezzo) a favore di trend (come limit) o contro-trend a scopo difensivo.
2.  **FASE 2 (Ticket & Satelliti):** 
    *   **Ticket:** Quando la posizione è in sicurezza, il sistema gioca a "Ping-Pong" prendendo piccoli profitti a pendolo usando la Mezza Size.
    *   **Standby:** Se il prezzo esce dal canale di sicurezza, il Motore attende che il prezzo ritracci per non rischiare slippage/rifiuti da IG.
    *   **Satelliti (OCO):** Ordini Stop piazzati sopra e sotto il prezzo. Una volta innescato il SAT1, vengono piazzati `OverGain` e `OverLoss`.
3.  **FASE 3 (Recovery Extremo / Tagli):**
    *   Se l'operazione va contro, il sistema inizia a chiudere parzialmente la posizione perdente (Taglio 1 al 35%, Taglio 2 totale) mentre monetizza nuove operazioni a favore.
4.  **RECOVERY MANUALE:** Strumento tattico nella Dashboard che calcola il prezzo teorico matematico mancante e permette all'utente di piazzare un `LIMIT`, uno `STOP` o un ingresso a `MERCATO` forzato.

## 4. DESIGN PATTERN E SCELTE TECNICHE PREGRESSE
Perché il codice è scritto in un certo modo? Ecco lo storico delle decisioni prese:

### Sulla Dashboard (Streamlit):
*   **Fragment (`@st.fragment`):** Usiamo i frammenti temporizzati (`run_every=15`) in Streamlit. Questo permette di aggiornare i prezzi live, la sidebar e il portafoglio ogni 15 secondi senza dover ricaricare l'intera pagina web.
*   **Tabelle HTML/CSS Custom:** Le tabelle del "Portafoglio IG" e delle "Statistiche" non usano i DataFrame standard di Streamlit. Usiamo HTML e CSS iniettato con `unsafe_allow_html=True` per:
    *   Togliere le barre di scorrimento laterali/verticali.
    *   Centrare perfettamente i testi e i numeri.
    *   Avere un ordinamento in *Master Row* (Grassetto, per la posizione Core) e *Sub-Row* (Leggero, per le size frazionate figlie della Core).

### Sul Motore (Python):
*   **Gestione Errori IG (403):** L'API di IG ha limiti di richiesta. Il codice usa una funzione `chiamata_api_sicura` con ciclo di `retry`. Se IG risponde con *HTTP 403 Exceeded API Key*, il sistema va automaticamente in pausa per 30 secondi prima di riprovare.
*   **Rifiuti Asincroni (Falsi Allarmi):** Spesso l'API IG accetta un ordine ma lo scarta pochi millisecondi dopo. C'è una funzione `verifica_falso_allarme_ig` che mette il Motore in pausa per 6 secondi per dare tempo ai server IG di allinearsi prima di dichiarare un ordine "mancante".
*   **Statistiche Chirurgiche (CSV):** *ATTENZIONE.* In passato il Motore interrogava lo storico API di IG per sapere quanto aveva guadagnato, causando ritardi e generando "Fasi SCONOSCIUTE" nel database. Oggi il Motore usa la funzione `registra_operazione(nome, fase_label, pnl)`. Questa viene triggerata *nell'esatto millisecondo* in cui il Motore chiude una posizione in gain/loss, garantendo dati perfetti, zero errori di denominazione e scartando gli eventi a importo € 0.00.
*   **Notifiche NTFY:** Ogni evento rilevante chiama `invia_notifica()`, che fa un POST HTTP verso un server ntfy.sh privato.

## 6. DIRETTIVE PER L'AI
Quando l'utente richiede una modifica:
1. Rispetta rigorosamente la separazione tra `Motore.py` e `Dashboard.py`. Non unire mai le logiche.
2. Mantieni lo stile CSS personalizzato nella Dashboard. Non regredire alle tabelle `st.dataframe` a meno che non sia esplicitamente richiesto, perché distruggerebbe il layout compatto e senza scrollbar creato finora.
3. Nei log o nelle nuove fasi del Motore, mantieni il tone-of-voice descrittivo ed "emotivo" dei log (es. uso di emoji 🚀, 🛑, ✂️).
4. Ogni modifica alla scrittura del CSV deve preservare la retrocompatibilità (Strumento, Fase, PNL, Deal_ID).
